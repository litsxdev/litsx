# `@litsx/unocss`

UnoCSS integration for LitSX components.

```js
import { presetWind3 } from "unocss";
import { defineConfig } from "vite";
import { litsxUnoCss } from "@litsx/unocss/vite";

export default defineConfig({
  plugins: litsxUnoCss({
    unocss: {
      presets: [presetWind3()],
    },
  }),
});
```

The adapter compiles LitSX first and adds one UnoCSS Shadow DOM placeholder per
module. Every LitSX component generated by that module references the same
utility `CSSResult`. A project-level virtual module exports the preflight as a
second shared `CSSResult`, preventing every component module from embedding its
own reset. Existing `Component.styles` values are preserved between the shared
preflight and the generated utilities.

The shared preflight is generated from UnoCSS's resolved project configuration
and aggregate token set. This preserves token-dependent theme variables from
presets such as Wind4, follows external `uno.config` files, and invalidates the
virtual stylesheet when development tokens or configuration change.

This package deliberately uses the compiler's generic `outputPlugins` hook.
There is no UnoCSS-specific behavior in `@litsx/compiler` or the JSX syntax.

Storybook can use the same compiler contribution and place the UnoCSS plugins
in its generic post-LitSX phase:

```js
import { createLitsxStorybookConfig } from "@litsx/storybook";
import {
  createUnoCssVitePlugins,
  withUnoCssViteCompiler,
} from "@litsx/unocss/vite";
import { presetWind3 } from "unocss";

export default createLitsxStorybookConfig({
  compiler: withUnoCssViteCompiler(),
  vitePlugins: {
    afterLitsx: createUnoCssVitePlugins({ presets: [presetWind3()] }),
  },
});
```

## Granularity and SSR

UnoCSS shadow-dom mode extracts at module granularity. Components declared in
the same module therefore share the union of that module's utility rules. This
does not duplicate CSS in the JavaScript module, but individual shadow roots
adopt rules used by sibling components from the same source module.

In the browser, importing the virtual preflight module gives every component
the same constructible stylesheet. During SSR the preflight must still be
serialized inside every declarative shadow root; a document-level stylesheet
cannot cross a shadow boundary.
